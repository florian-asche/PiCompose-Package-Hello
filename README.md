# PiCompose-Package-Hello

Example package `picompose-hello` for the [PiCompose APT repository](https://github.com/florian-asche/PiCompose-Repository). It prints a greeting and exists to test the build, signing and publishing pipeline end to end. It is not needed on a real device.

The repository is also meant as a template: copy it as a starting point for a package of your own.

## Install

Add the PiCompose APT repository (see [its documentation](https://github.com/florian-asche/PiCompose-Repository/blob/main/docs/apt_repository.md)), then:

```sh
sudo apt install picompose-hello
picompose-hello
```

## Layout

```
debian/
  control           package metadata, build dependencies, architecture
  changelog         placeholder, generated by the build
  rules             build instructions (plain dh)
  install           which files go where
  copyright         license
  source/format     3.0 (native): the version has no Debian revision
picompose-hello     the script installed to /usr/bin
```

## Using it as a template

1. Copy the repository and name it `PiCompose-Package-<Name>`.
2. Rename the source and binary package in `debian/control` and the name in `debian/changelog`. Package names start with `picompose-`.
3. Set `Architecture: all` for scripts, configuration and device tree overlays, and `any` for compiled content. This example uses `any` so that it is built for `amd64`, `arm64` and `armhf`, which exercises the multi-architecture pipeline.
4. Replace the script and `debian/install` with your own files, and adjust `debian/copyright` and `LICENSE`.
5. Add the repository to `sources.yml` of the APT repository and add the secret `HUB_DISPATCH_TOKEN` to it.

## Versioning and changelog

`debian/changelog` is generated by the build, so you do not edit it. The file in git is a placeholder. The generated changelog is part of the package (`apt changelog picompose-hello`).

- **Next version:** The newest release tag is raised by the text of every commit since that tag (commit message plus title and description of its pull request). `#major` raises the major version, `#minor` the minor version, anything else the patch version. The highest marker wins.
- **Push to `main`:** `<next version>~git<timestamp>.<sha>` is published to the suite `trixie-nightly`. The changelog entry is the title and description of the pull request.
- **Published release `v<version>`:** The tag has to be exactly the next version, otherwise the build fails and names the expected one. That version is published to the suite `trixie`, with the release text as changelog entry.
- **Any other branch:** `<next patch version>~dev<timestamp>.<sha>`. Nothing is published, the packages are kept as workflow artifacts for 14 days. Use a branch per change to try it on a device.

## Local build

```sh
sudo apt install build-essential debhelper devscripts fakeroot lintian
dpkg-buildpackage -us -uc -b
lintian ../picompose-hello_*.deb
```

The `.deb` files are written to the parent directory.

## Publishing

The workflow `.github/workflows/build.yml` calls the reusable workflow of the [PiCompose-Repository](https://github.com/florian-asche/PiCompose-Repository), which builds the package and tells the APT repository to publish it.

| Event | Result | Version |
| --- | --- | --- |
| Published release `v<version>` | suite `trixie` | `<version>` |
| Push to `main` | suite `trixie-nightly` | `<next version>~git<timestamp>.<sha>` |
| Push to another branch, pull request from a fork | artifact for 14 days | `<next patch version>~dev<timestamp>.<sha>` |

Create a GitHub release with the tag of the next version, and let GitHub generate the notes from the merged pull requests. The workflow attaches the packages to it. The repository needs the secret `HUB_DISPATCH_TOKEN`, see the [DEVELOPMENT.md](https://github.com/florian-asche/PiCompose-Repository/blob/main/DEVELOPMENT.md) of the APT repository.
